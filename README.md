# mongodb

База happydebt. В неё ходят `homebank_pull_info`, `bailiff_aisoip`, `crosschat` и другие
сервисы — то есть в коллекциях лежат данные должников.

## Запуск

```bash
cp .env.example .env
$EDITOR .env                 # проверить MONGO_DATA_DIR
chmod 600 .env
docker network create local-network   # если сети ещё нет (она общая, external)
docker compose up -d
```

## Где лежат данные

`${MONGO_DATA_DIR}` — по умолчанию `/srv/data/mongodb`, **вне каталога репозитория**.

Это отличается от `minio` и `file_service`, где данные лежат в `./data` рядом с compose,
и отличается намеренно. Каталог проекта на хосте — рабочая копия git; одна `git clean -xfd`
в нём удалила бы базу целиком. Для файлового хранилища это неприятно, для БД — потеря всего.

Соглашение: **код в `/srv/<проект>`, данные в `/srv/data/<проект>`.**

Права выставлять руками не нужно: официальный образ `mongo` стартует от root и сам
назначает владельца каталогу. (У прежнего образа `mongodb-enterprise-server` это не так —
он работает сразу от `mongod` и на чужом каталоге падает с
`Attempted to create a lock file on a read-only directory`.)

## 🔴 Миграция с именованных томов

Раньше данные лежали в томах `mongodb_data` и `mongodb_config`. **Сами они не переедут** —
без переноса Mongo поднимется на пустом каталоге и заведёт базу с нуля. Сервис при этом
будет выглядеть совершенно здоровым, просто без данных.

```bash
cd <каталог с docker-compose.yml>
docker compose down

SRC_DATA=$(docker volume inspect -f '{{ .Mountpoint }}' <имя_тома_data>)
SRC_CONF=$(docker volume inspect -f '{{ .Mountpoint }}' <имя_тома_configdb>)

sudo mkdir -p /srv/data/mongodb/db /srv/data/mongodb/configdb
sudo rsync -aH --info=progress2 "$SRC_DATA"/ /srv/data/mongodb/db/
sudo rsync -aH --info=progress2 "$SRC_CONF"/ /srv/data/mongodb/configdb/
sudo du -sh "$SRC_DATA" /srv/data/mongodb/db     # объёмы должны совпасть

docker compose up -d
docker compose logs -f mongodb                   # убедиться, что база открыла файлы
```

Старые тома сразу не удаляйте — пусть полежат страховкой, пока не убедитесь, что всё на месте.

## Редакция и версия

Было `mongodb/mongodb-enterprise-server:4.4.8-ubi8` — платная редакция. Лицензии нет
(подтверждено 10.08.2026), поэтому перешли на **Community** `mongo:4.4` (сейчас 4.4.30 —
это тот же 4.4, но с накопленными исправлениями).

Данные между Enterprise и Community одной версии совместимы: тот же WiredTiger.
Но если на боевой базе включались функции только Enterprise — аудит, шифрование
хранилища, in-memory движок, LDAP — переход их отключит. Перед переключением прода
это стоит проверить.

## Версия и требование AVX

Сейчас **8.0** (Community). До 10.08.2026 стояла 4.4, и не по выбору: MongoDB 5.0 и новее
требуют инструкций AVX, а виртуалки его не видели.

Починили сменой типа процессора у ВМ в Proxmox. Стало:

```
vm-stage:  avx avx2 fma bmi2      → mongo 8.0.28 работает
```

Ступенчатое обновление не понадобилось — база была пустая, поставили целевую версию сразу.

⚠️ **Требование AVX никуда не делось.** Если поднимать стек на другой машине — сначала:

```bash
grep -o -m1 avx /proc/cpuinfo     # должно вывести avx
```

Если пусто, контейнер не стартует с сообщением
`WARNING: MongoDB 5.0+ requires a CPU with AVX support`. Лечится там же, в Proxmox:

| Уровень | Что добавляет |
|---|---|
| `x86-64-v2` | SSE4.1, SSE4.2, POPCNT — **AVX нет** |
| **`x86-64-v3`** | **AVX**, AVX2, FMA, BMI1/BMI2, MOVBE |
| `x86-64-v4` | AVX-512 |

Годятся `host`, `x86-64-v3` или именованные модели от `SandyBridge` и новее.
Умолчание Proxmox 8 — `x86-64-v2-AES`, и оно **не подходит**.

Порядок: выключить ВМ → Hardware → Processors → **Type** → `host` или `x86-64-v3` →
включить → проверить `grep -o -m1 avx /proc/cpuinfo`.

**Важно на будущее:** пока база пустая, версию можно менять одной строкой в `.env`.
Как только в неё начнут писать, прыгать через мажорные версии станет нельзя — Mongo
обновляется последовательно (`5.0 → 6.0 → 7.0 → 8.0`), на каждом шаге с бэкапом и
`db.adminCommand({setFeatureCompatibilityVersion: "<версия>"})`.

### Про 192.168.127.103

На машине с Jenkins AVX **не включали** — там базы нет, только сборка. Понадобится, если
у сервисов, работающих с Mongo, появятся интеграционные тесты, поднимающие её в сборке.

### Чем `host` отличается от именованной модели

С `host` гость видит процессор узла целиком. Отсюда ограничение: **живая миграция на узел
с другим процессором ломается** — гость может выполнять инструкции, которых на целевом узле
нет. То же касается восстановления бэкапа или снапшота на другом узле и автоматического
переезда при отказе.

Именованная модель (`x86-64-v3`) даёт одинаковый виртуальный процессор на всех узлах, и
миграция работает — ценой того, что более новые расширения железа гостю недоступны.

**Как выбирать:** один узел Proxmox или миграция не используется → `host`, это проще.
Несколько узлов и миграция нужна → `x86-64-v3`, предварительно убедившись, что его
поддерживают все узлы.

### Порядок обновления, когда AVX появится

**Данных в базе нет** (подтверждено владельцем 10.08.2026), поэтому ступенчатое обновление
не нужно — ставим целевую версию сразу:

```bash
# в .env
MONGO_VERSION=8.0

docker compose up -d
docker compose logs -f mongodb     # дождаться "Waiting for connections"
```

Целевая версия — **8.0**. Требует AVX (см. выше), поэтому переключать только после смены
типа процессора у ВМ.

⚠️ **Это верно только пока база пустая.** Как только в ней появятся данные, перепрыгнуть
через мажорные версии уже нельзя: Mongo обновляется последовательно, и на каждом шаге
нужно поднимать `featureCompatibilityVersion`, иначе следующая версия не запустится:

```
4.4 → 5.0 → 6.0 → 7.0 → 8.0
```

На каждом шаге: бэкап → сменить `MONGO_VERSION` → `docker compose up -d` → дождаться
готовности → `db.adminCommand({setFeatureCompatibilityVersion: "<версия>"})`.

Поэтому версию стоит поднять **до** того, как в базу начнут писать — сейчас это одна строка,
потом станет процедурой на несколько часов.

## 🔴 Аутентификации нет

У базы **не включена аутентификация**, а порт открыт наружу — подключиться и прочитать
данные может кто угодно в сети. Ни один из сервисов-потребителей не использует логин и
пароль (проверено по их `.env.example`).

Решено вынести в отдельную задачу: к базе ходит много сервисов, и включение `--auth`
без предварительной раздачи учётных данных положит их разом. Порядок будет такой:
завести пользователей → раздать в `.env` каждого сервиса → включить `--auth` →
закрыть порт (`MONGO_BIND=127.0.0.1`).

## Чего ещё нет

**Бэкапов.** Совсем. Для базы с данными должников это стоит закрыть в первую очередь —
`mongodump` по расписанию с ротацией, как сделано для Jenkins.
